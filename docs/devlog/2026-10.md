## 2026-10-02 - Commit files: a project path must be plain segments

### Result

- `GET /api/commit-files` refuses a `project_path` that is not plain segments with `400 bad_request`, before config is read. A plain segment is letters, digits, `_`, `.` and `-`; it does not start with `-` and is never `.` or `..`. There is no empty, encoded, query or fragment part.
- The GitHub and GitLab commit-file readers apply the same check, and GitHub's narrower owner rule, to any path they are handed, a configured one included. They make no request for a path that fails, and they encode every segment they send.

### Why / context

- Code scanning (`js/request-forgery`) traced the query parameter into the GitHub reader's `repos/{owner}/{name}/commits/{sha}` URL. The GitHub reader split the path on `/` and put the two parts into that URL as they were.
- The route already required an exact match with a configured project before any provider call. So a request could not steer the path unless the configuration itself held such a path.
- The analyzer cannot see that membership test as a barrier. And a mistyped configuration entry should not become a way to reach another API path. So the check now sits where the value enters a URL, as a segment rule plus per-segment encoding.
- Real project paths keep passing: nested GitLab groups, dotted and underscored names, a GitHub `.github` repository, and managed-user owners (`name_shortcode`).

### Evidence

- Test first: three new tests in `test/commit-files.test.ts` failed on the unfixed code.
  - The parser accepted `../../user/repo`, and the route accepted `o/r?per_page=100` from config.
  - The GitHub reader requested `repos/o/r?x=1/...`.
  - After the fix they pass, along with the existing allowlist and sync-pass tests.
- `bash .agents/scripts/pre-pr.sh` (typecheck and `pnpm test`): 788 pass.
- A GitHub `--dry-run` sync of the demo configuration: status ok.

- [`DESIGN.md`](../DESIGN.md), commit files, Safety model.

## 2026-10-01 - Comment activity rows name their issue or change request (contract 4.9.1)

### Result

- Comment rows now carry `target_ref` and, when the producer stored none, the
  target's `title`. GitLab builds the ref in `normalize` (`gitlab/13`) from
  the note's `noteable_id`, or an issue or merge request event's `target_id`.
  GitHub's is resolved at emit time from the row's repository, kind and number
  against the live items.
- A range response now emits the item any in-range row names as an
  `activity_target` support row, not only a review's change request.
- Contract `4.9.1`, a clarification: no field was added. This is item A1 of the
  Activity page work in #768.

### Why / context

- On the live board, comment rows were about 30% of the emitted feed
  (11,317 of 38,176), and every one had `target_ref: null` and `title: null`.
  A GitHub comment could say only "commented · change request #36". The
  Activity detail pane (#768, A2) needs the item's title, state and labels.
- GitHub's REST comment payloads carry no node id for their issue or pull
  request. One lookup per comment is a different cost class, so the join is
  done at emit time. It resolves to the item's immutable ref, and a miss leaves
  `null`, so the identity rule is not keyed on the number. It applies to every
  stored row at once.
- An old GitLab test asserted that "REST target_id is not the GraphQL global
  id". The id's format differs, but its number is the same database id. Before
  relying on that, a read-only query against a production store matched every
  one of 2,965 GitLab note, issue and merge-request events to a stored item
  through `gid://gitlab/<Type>/<id>`. The test now asserts the ref.
- Comment text stays out of the contract on purpose. The UI will show a
  comment's words only where `review_threads[]` already carries them.

### Evidence

- Test first: three build tests (range support rows, comment resolution, static
  contract) and two GitLab normalizer tests failed before the change. Two
  existing assertions changed meaning and were updated: the GitLab event target,
  and an in-range `closed` row now marks its primary item as an
  `activity_target` too.
- `pnpm run typecheck`; `pnpm test`: 785 pass. UI build, UI tests (569 pass)
  and the render smoke pass unchanged.
- A real full sync of two public repositories into a throwaway store, then
  `emit` and `validate`: all 3,124 comment rows in the 30-day window carried a
  ref and a title, and every ref was in the static contract's items.
- The production store's GitHub comment rows: 17,825 of 30,247 (all time)
  resolve against a live item, and no number is shared by two items. Most

## 2026-10-01 - Graph keeps a linked focus through the app's own loads

### Result

- A Graph focus that arrives with the route (a link, a reload, back/forward)
  survives the app's own loads: the cold start's range re-anchored to the
  contract's `generated_at`, and a contract reload. A tracker focus opened that
  way opens its program view.
- The focus is still dropped when the viewer changes the range or an item facet
  under the same focus and that changes which items the overview lists. The
  rule is pure: `graphFocusDropped` over `graphFocusLens` (the route's range
  and item facets) in `packages/ui/src/model.ts`.

### Why / context

- The Graph page dropped the focus whenever the overview candidate membership
  changed between two renders. That was meant for a viewer's range or facet
  change, but a cold start without a route range loads twice (the range seeded
  from the clock, then re-anchored to `generated_at`), and a months-old
  contract makes the two loads differ. The page could not tell that second load
  from a viewer's change, so the focus was cleared before the item or its
  program was requested. A background reload that changed the relations did the
  same.
- Candidates are now compared only across a lens change under the same focus. A
  new focus starts a new baseline, so a link that brings its own range or
  facets keeps its focus too. The comparison itself is unchanged: a facet that
  changes the listed items drops the focus even when the focused item stays
  listed.
- While focused, the range control is suspended, so a range change comes only
  from the route. Its client-side filter applies in the same render and counts;
  the range load that follows does not.
- This fixes the follow-up left in the 2026-09-30 Graph program view entry,
  which stays as written (the log is append-only).

### Evidence

- Test first: two unit tests (`graphFocusDropped`, `graphFocusLens`) failed by
  assertion against an inert stub that carried the old rule. Two render-smoke
  checks reload `#/graph?focus=<ref>` without a range, for an ordinary item and
  for the sample tracker `ISSUE_c`; on the unfixed code both came back as
  `#/graph` (523 pass, 2 fail).
- Those checks answer ranges with the harness's 500 ms startup delay, so the
  lazily loaded Graph page mounts on the first load. Without it the second load
  could land first, and the unfixed code passed 2 of 2 runs. The existing

- After the fix: `bash .agents/scripts/pre-pr.sh` (typecheck and `pnpm test`):
  782 pass. `pnpm --filter @symphony-board/ui run test`: 568 pass. The UI
