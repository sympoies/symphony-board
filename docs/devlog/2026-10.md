## 2026-10-01 - Commits: a laptop tier with the wide tier's panes

### Result

- From 1400px to 2479px the Commits supporting columns carry the wide tier's
  panes (every summary tile, the stacked per-day chart, lines changed, the
  day-by-hour grid, Largest commits, Change requests; ranked rows with their
  facts; the Hot files pane), stacked one module per column at 36 / 32 / 32,
  each column scrolling inside itself. From 1960px the split goes back to
  40 / 30 / 30, where that keeps the list on its one-line rows.
- In every three-column layout the list's wrapping card puts the sha and its
  actions beside the subject only, so the lines under it use the card's full
  width; a card is about 20px shorter and its branch chips stop clipping.
- The toolbar puts the source chips beside the pickers in the laptop tier,
  which gives the panes a line.

### Why / context

- The wide tier (2480px up) read well on a desktop monitor, while a laptop's
  built-in screen (1512x982 on a 14" MacBook Pro at default scaling) fell back
  to the plain digest: six tiles, day bars, an hour strip and four bar charts,
  the same bar drawn five times.
- The limit on a laptop is width, not height: one ~430px module per column,
  not two. So the tier reuses the wide tier's panes and changes only the
  layout. Its stylesheet block repeats the rows relayout for its own rail
  rather than widening the 2200px rows block, which also lays out Activity's
  rail and the wide tier.
- Stacked-day and churn tooltips list every series and were wider than the
  column; in this tier they are a readout in the plot's top corner.

### Evidence

- `layout-tier.test.ts` asserts the tier constants and the stylesheet block in
  step; the render smoke asserts the tier at 1512x945 (both columns stacked and
  scrolling, level with the list, rows with facts, cards using their full
  width, nothing wider than its pane) and keeps the plain digest's checks at
  1360px, below the tier.
- Checked by screenshot against a live contract at 1360x900, 1470x900,
  1512x945, 1728x1080 and 2300x1300.

## 2026-10-01 - Graph keeps a linked focus through the app's own loads

### Result

- A Graph focus that arrives with the route (a link, a reload, back/forward)
  survives the app's own loads: the cold start's range re-anchored to the
  contract's `generated_at`, and a contract reload. A tracker focus opened that
  way opens its program view.
- The focus is still dropped when the viewer changes the range or an item facet
  under the same focus and that changes which items the overview lists. The
  rule is pure: `graphFocusDropped` over `graphFocusLens` (the route's range
  and item facets) in `packages/ui/src/model.ts`.

### Why / context

- The Graph page dropped the focus whenever the overview candidate membership
  changed between two renders. That was meant for a viewer's range or facet
  change, but a cold start without a route range loads twice (the range seeded
  from the clock, then re-anchored to `generated_at`), and a months-old
  contract makes the two loads differ. The page could not tell that second load
  from a viewer's change, so the focus was cleared before the item or its
  program was requested. A background reload that changed the relations did the
  same.
- Candidates are now compared only across a lens change under the same focus. A
  new focus starts a new baseline, so a link that brings its own range or
  facets keeps its focus too. The comparison itself is unchanged: a facet that
  changes the listed items drops the focus even when the focused item stays
  listed.
- While focused, the range control is suspended, so a range change comes only
  from the route. Its client-side filter applies in the same render and counts;
  the range load that follows does not.
- This fixes the follow-up left in the 2026-09-30 Graph program view entry,
  which stays as written (the log is append-only).

### Evidence

- Test first: two unit tests (`graphFocusDropped`, `graphFocusLens`) failed by
  assertion against an inert stub that carried the old rule. Two render-smoke
  checks reload `#/graph?focus=<ref>` without a range, for an ordinary item and
  for the sample tracker `ISSUE_c`; on the unfixed code both came back as
  `#/graph` (523 pass, 2 fail).
- Those checks answer ranges with the harness's 500 ms startup delay, so the
  lazily loaded Graph page mounts on the first load. Without it the second load
  could land first, and the unfixed code passed 2 of 2 runs. The existing
  reload checks that keep the range on the route stay; they cover the one-range
  path.
- A third smoke check picks a kind facet in focus and sees the focus dropped.
- After the fix: `bash .agents/scripts/pre-pr.sh` (typecheck and `pnpm test`):
  782 pass. `pnpm --filter @symphony-board/ui run test`: 568 pass. The UI
  build, then the render smoke three runs in a row, 526 assertions each. `pnpm
  run validate --in packages/ui/public/contract.json`: valid.
