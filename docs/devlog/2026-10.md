## 2026-10-01 - Activity: the Commits pane tiers, with Activity's own panes

### Result

- From 1400px the Activity page has three columns, using the Commits page's
  tiers: one pane per column on a laptop (1400-2479px), two-up from 2480px.
- The middle column holds the detail above an overview of panes:
  - summary tiles;
  - the year's rhythm with its facts;
  - events per day, stacked by kind, action, repository or person;
  - a day-by-hour grid;
  - review verdicts;
  - the busiest issues and change requests, each opening its newest event.
- The rail holds Who and Where as tables with share, active days and per-day
  sparklines, then Branches, What and How. Where, What, How and a verdict toggle
  the page's facets.
- Item A3 of #768. There is no contract change.

### Why / context

- The Activity layout is also a `.commits-split` in these tiers, and its panes
  use the Commits pane classes (`.commits-context`, `.commits-overview`,
  `.commits-rail` with `data-panes`). The tier rules, scrolling columns and
  two-up grids are therefore written once for both pages, instead of copied.
  The Activity rail takes the Commits rail's five slots, so the same grid
  rows fit.
- `CommitDayChart` became a generic `StackedDayChart`, the punch card and the
  rhythm calendar take a noun and a kind, and the ranked-row parts (sparkline,
  column head, share, age) moved to `RankParts.tsx`. Activity reuses all of
  them rather than forking.
- The old who / where / when rail (1700px and up) would never render once the
  tiers start at 1400px. Its component, constant and CSS are removed.
- Review verdicts are drawn as a short table, not a ranked chart. Only the
  rail relays charts into rows; four vertical bars beside the punch card said
  less than four rows.
- In the wide tier Where sits in a half-width pane. With the people and
  last-event columns too, the first smoke run measured its bars at 3px with the
  counts overflowing. Those two facts stay in the row's accessible name.

### Evidence

- Test first: four `rail-stats` aggregates (`activityTotals`,
  `rankReviewVerdicts`, `busiestItems`, `repoActivityDetails`) failed on the
  missing exports before they existed. The layout-tier tests for the old rail
  were replaced by one that pins Activity to the shared pane queries and the
  removal of `.activity-rail`.
- The render smoke gained two checks: the pane tiers at 2560px and 1512px, and
  the interactions (re-split by actor, a busiest item, a Where facet). Existing
  checks moved from `.activity-rail` and `.activity-heatmap` to the new rail
  and overview. The trend-line check moved to 1280px, where the plain overview
  still draws it.
- `pnpm run typecheck`; `pnpm test`; UI tests; UI build; render smoke PASS.
- Screenshots at 2560x1440, 2000x1200 and 1512x945, against a contract emitted
  from a real sync of two public repositories.

## 2026-10-01 - Activity: compact rows and a detail pane for the selected event

### Result

- Activity rows are two lines of 60px (a phone: 82px), down from cards of 118px
  that held one line of facts. A row names the item it is about, with its
  number, title and current state, or a commit's short sha, subject and line
  counts, or a push's ref and from -> to.
- Selecting a row opens a detail pane above the overview. It shows the item as
  it is now, the event's own facts, a review comment's words when
  `review_threads[]` carries them, and the other in-range events on the same
  item. A wide screen opens it on the newest event, pinned. Below 1212px it is a
  route-backed reader (`activityDetail=1`) with previous / next and swipe.
- Item A2 of #768. No contract change: it reads what 4.9.1 (A1) emits.

### Why / context

- The maintainer asked for Activity to be as dense and navigable as Commits. On
  the live board the feed's cards were mostly empty space, and nothing on the
  page showed more than a row's single line.
- A comment row is about 30% of the feed. Since 4.9.1 it names its item, so the
  row and the pane can show the PR or issue title, state and labels.
- Comment words: the contract has none on activity rows by design. The pane
  quotes only a review-thread comment the contract already carries for the
  Reviews page, so this shows no text the board did not already show. An issue
  comment shows no excerpt.
- Below the split floor the overview stacks under the feed, so a pane inserted
  above it would open out of sight. There, as on a phone, the row opens a
  reader.
- Review moved the default from following the newest event to pinning it. With
  following, a sync or refresh with a newer row swapped the event under the
  reader. Following is now opt-in, as on Commits. A reader whose event drops
  out of the list closes rather than switching to another event.
- The render smoke inflates the sample to 1,200 rows by cycling `i % rows`. The
  two new sample comment rows are carried once at the head instead, because
  cycling them would reshuffle every synthetic commit the Commits checks count.
  Inserting them into the cycle first failed two Commits checks, which is how
  that dependence was found.

### Evidence

- Test first: `test/activity-detail.test.ts` (8 tests) failed on the missing
  module. The `activityDetail` route and `workItemDestination` tests failed
  before the route field and the helper existed.
- The render smoke gained four Activity checks: the following pane, a pinned
  review comment with its words, close and follow-latest, and the phone reader.
  Four existing Activity checks changed with the row shape: the headline text,
  the row budget (a two-line title became one line, at 60px), the phone chips,
  and the rhythm column's position, now that the detail sits above the overview.
- `pnpm run typecheck`; `pnpm test`; UI tests (578 pass); UI build; render smoke
  PASS.
- Screenshots at 2000x1200 and 390x844, against a contract emitted from a real
  sync of two public repositories.

## 2026-10-01 - Comment activity rows name their issue or change request (contract 4.9.1)

### Result

- Comment rows now carry `target_ref` and, when the producer stored none, the
  target's `title`. GitLab builds the ref in `normalize` (`gitlab/13`) from
  the note's `noteable_id`, or an issue or merge request event's `target_id`.
  GitHub's is resolved at emit time from the row's repository, kind and number
  against the live items.
- A range response now emits the item any in-range row names as an
  `activity_target` support row, not only a review's change request.
- Contract `4.9.1`, a clarification: no field was added. This is item A1 of the
  Activity page work in #768.

### Why / context

- On the live board, comment rows were about 30% of the emitted feed
  (11,317 of 38,176), and every one had `target_ref: null` and `title: null`.
  A GitHub comment could say only "commented · change request #36". The
  Activity detail pane (#768, A2) needs the item's title, state and labels.
- GitHub's REST comment payloads carry no node id for their issue or pull
  request. One lookup per comment is a different cost class, so the join is
  done at emit time. It resolves to the item's immutable ref, and a miss leaves
  `null`, so the identity rule is not keyed on the number. It applies to every
  stored row at once.
- An old GitLab test asserted that "REST target_id is not the GraphQL global
  id". The id's format differs, but its number is the same database id. Before
  relying on that, a read-only query against a production store matched every
  one of 2,965 GitLab note, issue and merge-request events to a stored item
  through `gid://gitlab/<Type>/<id>`. The test now asserts the ref.
- Comment text stays out of the contract on purpose. The UI will show a
  comment's words only where `review_threads[]` already carries them.

### Evidence

- Test first: three build tests (range support rows, comment resolution, static
  contract) and two GitLab normalizer tests failed before the change. Two
  existing assertions changed meaning and were updated: the GitLab event target,
  and an in-range `closed` row now marks its primary item as an
  `activity_target` too.
- `pnpm run typecheck`; `pnpm test`: 785 pass. UI build, UI tests (569 pass)
  and the render smoke pass unchanged.
- A real full sync of two public repositories into a throwaway store, then
  `emit` and `validate`: all 3,124 comment rows in the 30-day window carried a
  ref and a title, and every ref was in the static contract's items.
- The production store's GitHub comment rows: 17,825 of 30,247 (all time)
  resolve against a live item, and no number is shared by two items. Most
  misses are items that are no longer live.

## 2026-10-01 - Graph keeps a linked focus through the app's own loads

### Result

- A Graph focus that arrives with the route (a link, a reload, back/forward)
  survives the app's own loads: the cold start's range re-anchored to the
  contract's `generated_at`, and a contract reload. A tracker focus opened that
  way opens its program view.
- The focus is still dropped when the viewer changes the range or an item facet
  under the same focus and that changes which items the overview lists. The
  rule is pure: `graphFocusDropped` over `graphFocusLens` (the route's range
  and item facets) in `packages/ui/src/model.ts`.

### Why / context

- The Graph page dropped the focus whenever the overview candidate membership
  changed between two renders. That was meant for a viewer's range or facet
  change, but a cold start without a route range loads twice (the range seeded
  from the clock, then re-anchored to `generated_at`), and a months-old
  contract makes the two loads differ. The page could not tell that second load
  from a viewer's change, so the focus was cleared before the item or its
  program was requested. A background reload that changed the relations did the
  same.
- Candidates are now compared only across a lens change under the same focus. A
  new focus starts a new baseline, so a link that brings its own range or
  facets keeps its focus too. The comparison itself is unchanged: a facet that
  changes the listed items drops the focus even when the focused item stays
  listed.
- While focused, the range control is suspended, so a range change comes only
  from the route. Its client-side filter applies in the same render and counts;
  the range load that follows does not.
- This fixes the follow-up left in the 2026-09-30 Graph program view entry,
  which stays as written (the log is append-only).

### Evidence

- Test first: two unit tests (`graphFocusDropped`, `graphFocusLens`) failed by
  assertion against an inert stub that carried the old rule. Two render-smoke
  checks reload `#/graph?focus=<ref>` without a range, for an ordinary item and
  for the sample tracker `ISSUE_c`; on the unfixed code both came back as
  `#/graph` (523 pass, 2 fail).
- Those checks answer ranges with the harness's 500 ms startup delay, so the
  lazily loaded Graph page mounts on the first load. Without it the second load
  could land first, and the unfixed code passed 2 of 2 runs. The existing
  reload checks that keep the range on the route stay; they cover the one-range
  path.
- A third smoke check picks a kind facet in focus and sees the focus dropped.
- After the fix: `bash .agents/scripts/pre-pr.sh` (typecheck and `pnpm test`):
  782 pass. `pnpm --filter @symphony-board/ui run test`: 568 pass. The UI
  build, then the render smoke three runs in a row, 526 assertions each. `pnpm
  run validate --in packages/ui/public/contract.json`: valid.
