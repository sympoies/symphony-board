# 2026-08

## 2026-08-25 — Layout tiers read viewport height, not width alone

**Result**
- `packages/ui/src/layout-tier.ts` is now the single source of truth for the
  responsive breakpoints (narrow `<= 760px` wide, short `<= 760px` tall, split
  overlay `<= 900px` wide); `styles.css` mirrors them and `layout-tier.test.ts`
  fails if the two drift.
- A new compact-chrome tier (`@media (max-width: 760px), (max-height: 760px)`)
  folds the read-only vertical strips — Live metrics, the Board/Graph stats bar,
  repo analytics, commit filters — behind the disclosures they already had but
  that only existed at phone widths.
- `clampContentPaneHeight` gained a real 240px floor, document-relative pane
  tops, and an Android-inset-aware bottom gutter; every tab (Live, Items,
  Reviews, Board, Graph) now shares that one clamp instead of three variants.

**Why / context**
- Every breakpoint in the stylesheet was `max-width`. A device can clear all of
  them and still have no vertical room: a foldable's inner screen reports about
  933x704 CSS px, so it rendered the full desktop chrome — brand header, tabs,
  the four metric cards in a 2x2 grid, the filter bar — which spent ~595px of a
  704px viewport.
- What made that a hard failure rather than a cramped one was the pane model.
  `clampContentPaneHeight` returned exactly the space between the split and the
  viewport bottom, and treated its `min` as a soft hint on the reasoning that
  forcing the minimum "reintroduces document-level scrolling". It does, and that
  turned out to be the point: with the pane ending at the viewport bottom, the
  document is exactly viewport-height and has nothing to scroll. The feed was a
  93px sliver — less than one 114px row — with no way to reach anything below
  it. A phone in landscape and a half-height desktop window starve identically.
- Two orthogonal questions were being answered by one number. Whether two panes
  fit side by side is horizontal; whether a metric strip is affordable is
  vertical. Splitting them let the vertical strips join a width-or-height tier
  while the facet filters, date range and search stayed narrow-only — collapsing
  those is a horizontal decision, and their expanded state is a phone sheet a
  wide viewport should never see.
- The floor is 240px, not the previous 320px hint: two rows at the default
  two-line preview (114px row + 6px gap). Deliberately below what an ordinary
  desktop leaves over — a 1280x900 window leaves ~312px — so the no-scroll
  dashboard feel survives everywhere it already worked, and the floor only
  engages where the layout is genuinely broken.
- Pane tops are now measured as `rect.top + scrollY`. A viewport-relative top
  was fine while the document could never scroll; once the floor lets it, the
  same measurement would re-shrink the pane on every scroll tick.
- Separately, the bottom gutter was a flat 16px while `.app-wide` padding folds
  in `--android-safe-area-bottom`, so on an edge-to-edge WebView a pane's last
  rows sat under the opaque navigation-bar scrim.

**Evidence**
- `pnpm run typecheck && pnpm test` — 615 pass. `pnpm --filter
  @symphony-board/ui run typecheck|test|build|smoke` — 391 UI tests pass, smoke
  PASS.
- `layout-tier.ts` must stay DOM-free: `test/graph-neighborhood.test.ts` imports
  `model.ts`, which pulls it into the root type-check program (no DOM lib), so
  the runtime probes live in `useMediaQuery.ts` instead.
- render-smoke now drives the foldable geometry (933x704) directly. Collapsed
  metrics: feed pane 340px, 9 rows, first row inside the pane, document 704px so
  nothing needs to scroll. Metrics re-expanded: feed holds the 240px floor and
  the document grows to 937px, so the page scrolls to it. Before the change the
  same viewport produced a ~93px pane in a document that could not scroll.
- The render-smoke harness intermittently fails with a CDP
  `{"code":-32000,"message":"Promise was collected"}` before any assertion runs;
  a re-run passes. Unrelated to this change.

**Links**
- Commit: `fix(ui): size layout tiers on viewport height, not width alone`.
- Replaces the reasoning recorded in the old
  `clampLivePaneHeight fills the available viewport and never forces the
  minimum past it` test.

## 2026-08-25 — Web sidecar re-resolves its proxied upstreams

**Result**
- `docker/ui-nginx.conf` now reaches `board`, `api`, and `live` through
  per-request variables backed by the Docker embedded resolver instead of
  literal `proxy_pass` hostnames, so an upstream recreated on a new address is
  proxied to rather than 502'd against a dead one.
- The pg-compose smoke forces `api` onto a different container address and
  requires the proxy to follow it, so the regression cannot come back unseen.

**Why / context**
- nginx resolves a literal `proxy_pass` hostname exactly once, at config load,
  and pins that address for the worker's lifetime. Docker gives a recreated
  service a new address, and compose only recreates services whose own image or
  config changed — so an ordinary redeploy can move `api` or `live` while
  leaving the `web` sidecar untouched and pointing at addresses that no longer
  exist.
- The failure is close to invisible. `/` keeps serving the SPA from disk and the
  container keeps reporting healthy; only the proxied `/api/*` routes are dead,
  so nothing surfaces the break until someone opens the board. A live compose
  deployment of this stack went dark exactly that way after a routine redeploy.
  The first repair there was an operator-side restart hook, which treats the
  symptom during a deploy; this removes the cause and also covers an upstream
  that moves outside one.
- The `/api/` block needed the most care. `proxy_pass http://api:8081/api/;`
  carries a URI, so nginx replaces the matched location prefix with it — but
  that replacement is `/api/` → `/api/`, an identity mapping. Switching to a
  variable with no URI part forwards the original request URI unchanged, which
  is the same thing. Nothing under `src/` emits a `Location` header, so the
  implicit `proxy_redirect default` that a variable `proxy_pass` disables costs
  nothing here.
- `valid=10s` is deliberate: Docker's embedded DNS hands out a 600s TTL, which
  would cache the dead address straight back and undo the fix.
- One behaviour genuinely changes, and it is worth knowing about: nginx used to
  refuse to start at all when an upstream name did not resolve, so a stack
  missing `live` failed loudly at `web` startup. Deferred resolution means the
  sidecar now starts, serves the SPA, and 502s only that route. The loud failure
  moves to where it belongs — compose `depends_on` plus the deployment's own
  smoke, which already asserts `/`, `/api/live-snapshot`, and `/api/range`
  through the published web port.

**Behaviour change, measured**
- `docker run --entrypoint nginx <web:1.12.9> -t` →
  `[emerg] host not found in upstream "board"`, exit 1.
- The same test on the rebuilt image → `configuration file ... test successful`,
  exit 0.

**Evidence**
- Before: the smoke reported the forced move and then `GET /api/stats -> 502`
  for the full 60s recovery window; exit 1.
- After: same forced move, `web re-resolved api after the upstream moved`, exit
  0, with every pre-existing route assertion in the smoke still passing.
- Reproducing it needs the sentinel. Recreating `api` on its own usually gets
  the same address back from Docker's IPAM, so a naive version of this test
  passes against the broken config and proves nothing.
- `pnpm run typecheck`, `pnpm test` (612 passing), and `shellcheck` over
  `scripts/**` all clean.

**Links**
- `docker/ui-nginx.conf`, `scripts/ci/pg-compose-smoke.sh`.

**Follow-ups**
- A moved upstream still returns 502 for up to the resolver's `valid=10s`
  window before the proxy follows it. That is well inside the deploy gate's
  own wait, but a deployment that probes faster may want a short retry.
