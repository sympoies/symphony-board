## 2026-08-31 — Make five-minute sync starts wall-clock accurate

**Result**
- Release 1.13.6 is deployed with fixed-rate loop scheduling: an incremental
  run starts every five minutes when the preceding run fits in its slot.
- Missed deadlines are skipped without overlapping writers or catch-up bursts.
  Production uses 144 iterations per full sweep, preserving the approximately
  12-hour reconciliation cadence.

**Why / context**
- The prior loop slept for the configured interval only after a run completed.
  A five-minute setting therefore appeared as six to seven minutes in the UI
  once provider and emit work were included.
- Full sweeps remain iteration-based, so changing to fixed starts required a
  coordinated production count adjustment rather than only a scheduler patch.

**Evidence**
- Type-check and all 630 backend tests passed, including deterministic normal
  and overrun scheduler cases. The deployment repository's full validation and
  post-merge production health gate also passed.
- Consecutive deployed incremental iterations started at
  `2026-08-31T02:28:18.244Z` and `2026-08-31T02:33:18.249Z`, a 300.005-second
  interval. The initial full run exceeded one slot and correctly aligned the
  next start to the following cadence boundary.

## 2026-08-30 — Ship quota-efficient 10-minute reconciliation

**Result**
- Release 1.13.5 is deployed with the incremental pull-request detail expansion
  paid only for changed rows instead of every repository on every poll.
- Production now sleeps 10 minutes after each canonical run and performs a full
  sweep every 62 iterations, preserving an approximately 12-hour full-to-full
  cadence at the measured run duration.
- The release's arm64 macOS application and signed universal Android package
  were independently checksum-verified before device delivery.

**Why / context**
- Live webhooks remain the immediate path, but missed events still need a short,
  predictable reconciliation window. The previous fixed incremental expansion
  cost made 10-minute polling unsafe on a standard GraphQL bucket even when no
  pull requests had changed.
- The final full-sweep interval accounts for run duration as well as the
  post-run sleep. Multiplying 72 iterations by 10 minutes would have understated
  the wall-clock interval; 62 iterations keeps disappearance reconciliation
  close to twice daily under the observed production workload.

## 2026-08-30 — Remove fixed GitHub incremental PR expansion cost

**Result**

  ordered metadata query and resolve rich detail only for fresh rows; full
  sweeps retain the exhaustive rich connection.
- A production-config, read-only dry run reduced measured GraphQL cost from a
  profiled 2,267-point baseline to 141 points while completing successfully.

## 2026-08-30 — Make focused relationship exploration predictable

**Result**
- Focused Graph views now start at one hop and retain the viewer's chosen depth
  when focus is exited and re-entered during the same app session.
- Structural relationships can still expand through depths 2–5, while mentions
  are optional direct context around the selected item and do not become
  recursive traversal branches.
- The selected canvas node has a distinct focus treatment, and visible node/link
  counts follow the mention toggle.

**Why / context**
- Five-hop focus was technically bounded but not a useful default: dense mention
  links could pull most of the store into view and make a stable selection look
  as though it had jumped back to the all-items graph.
- Clearing `depth` together with `focus` also caused a genuine state regression:
  a viewer who explicitly chose one hop could return to the old default after
  leaving focus. The chosen depth is a viewing preference, not item identity, so
  it now survives that transition without being persisted across app sessions.
- The operational API keeps its previous recursive-mention default for existing
  callers; the UI explicitly requests the safer direct-mention mode.

**Evidence**
- Test-first coverage reproduced the five-hop default, recursive mention
  expansion, lost depth preference, and missing client query policy before the
  implementation.
- Type-check and all 626 backend tests passed; all 397 UI tests passed.
- The production UI build and browser render smoke passed, including default
  depth, depth refetching, stale-response rejection, direct mention requests,
  focus styling, and depth retention across focus exit/re-entry.

  App installations, retains the self-hosted GitLab source, and keeps personal

  responses up to three attempts with bounded 250 ms and 500 ms delays.

  body in both the Live feed and detail pane; commit events keep their existing

**Why / context**

  incremental sweep every hour and a full sweep every 12 iterations (twice

  masking authentication, rate-limit, GraphQL, transport, or server-code bugs.

## 2026-08-25 — Layout tiers read viewport height, not width alone

**Result**
- `packages/ui/src/layout-tier.ts` is now the single source of truth for the
  responsive breakpoints (narrow `<= 760px` wide, short `<= 760px` tall, split
  overlay `<= 900px` wide); `styles.css` mirrors them and `layout-tier.test.ts`
  fails if the two drift.
- A new compact-chrome tier (`@media (max-width: 760px), (max-height: 760px)`)
  folds the read-only vertical strips — Live metrics, the Board/Graph stats bar,
  repo analytics, commit filters — behind the disclosures they already had but
  that only existed at phone widths.
- `clampContentPaneHeight` gained a real 240px floor, document-relative pane
  tops, and an Android-inset-aware bottom gutter; every tab (Live, Items,
  Reviews, Board, Graph) now shares that one clamp instead of three variants.
- The tier reaches further than the devices that prompted it: at 760px it also
  catches a maximized browser on a 1366x768 or 1536x864 laptop (~640-660px of
  viewport). That is mostly where the biggest win landed — Live went from a ~90px
  sliver to a full pane on 768p laptops, which nobody had reported — but it also
  makes the Board/Graph stats strip and the repo-analytics grid default to
  collapsed there. Deliberate, one tap to undo, and remembered.

**Why / context**
- Every breakpoint in the stylesheet was `max-width`. A device can clear all of
  them and still have no vertical room: a foldable's inner screen reports about
  933x704 CSS px, so it rendered the full desktop chrome — brand header, tabs,
  the four metric cards in a 2x2 grid, the filter bar — which spent ~595px of a
  704px viewport.
- What made that a hard failure rather than a cramped one was the pane model.
  `clampContentPaneHeight` returned exactly the space between the split and the
  viewport bottom, and treated its `min` as a soft hint on the reasoning that
  forcing the minimum "reintroduces document-level scrolling". It does, and that
  turned out to be the point: with the pane ending at the viewport bottom, the
  document is exactly viewport-height and has nothing to scroll. The feed was a
  93px sliver — less than one 114px row — with no way to reach anything below
  it. A phone in landscape and a half-height desktop window starve identically.
- Two orthogonal questions were being answered by one number. Whether two panes
  fit side by side is horizontal; whether a metric strip is affordable is
  vertical. Splitting them let the vertical strips join a width-or-height tier
  while the facet filters, date range and search stayed narrow-only — collapsing
  those is a horizontal decision, and their expanded state is a phone sheet a
  wide viewport should never see.
- The floor is 240px, not the previous 320px hint: two rows at the default
  two-line preview (114px row + 6px gap). Deliberately below what an ordinary
  desktop leaves over — a 1280x900 window leaves ~312px — so the no-scroll
  dashboard feel survives everywhere it already worked, and the floor only
  engages where the layout is genuinely broken.
- Pane tops are now measured as `rect.top + scrollY`. A viewport-relative top
  was fine while the document could never scroll; once the floor lets it, the
  same measurement would re-shrink the pane on every scroll tick.
- Separately — and it is worth being explicit that this is a second, independent
  fix riding along, so a later bisect knows the two are separable — the bottom
  gutter was a flat 16px while `.app-wide` padding folds in
  `--android-safe-area-bottom`, so on an edge-to-edge WebView a pane's last rows
  sat under the opaque navigation-bar scrim.

**What review changed**
- The metrics default was originally seeded once at mount from
  `isShortViewport()` and immediately persisted by the save effect. That made an
  inferred default indistinguishable from an explicit choice — and broke on the
  exact device this was written for: a foldable owner who opens Live on the
  384x854 **cover** screen (narrow, but taller than the short breakpoint)
  persists "open", so unfolding to the inner screen kept the strip expanded
  forever. The collapse is now driven live by `useMediaQuery`, the stored value
  is a three-state choice (absent = never chosen), and only an explicit tap
  writes.
- The compact tier originally revealed the Commits repo/branch disclosure too.
  The sheet that disclosure opens is unhidden narrow-only, and the inline toolbar
  it replaces is hidden narrow-only, so on a short-but-wide viewport the tier
  *added* ~42px of dead chrome to the viewports it exists to give height back to.
  Commits went back to narrow-only, and the invariant it broke — a tier may
  reveal a disclosure only if it also reveals what that disclosure opens — is now
  asserted.
- "Every tab shares one clamp" was false when first written: `@media (max-width:
  1180px)` overrode Board and Graph with bare `vh` and no custom property, and
  that band contains the 933px foldable. Those three rules now take the shared
  variable, so the claim holds.
- `.live-feed`'s `72dvh` was briefly going to become `72svh` to stop it
  re-resolving as a mobile toolbar collapses. Refuted on review: `svh` pins the
  pane to the toolbar-*expanded* viewport and permanently wastes ~10% of the
  screen, which is the same class of bug this change fixes. The churn is bounded
  (an O(1) memoized range over a ~20-30 row slice, once per transition), so `dvh`
  stayed and `.activity-list` / `.commit-list` followed it.

**Evidence**
- `pnpm run typecheck && pnpm test` — 615 pass. `pnpm --filter
  @symphony-board/ui run typecheck|test|build|smoke` — 391 UI tests pass, smoke
  PASS.
- `layout-tier.ts` must stay DOM-free: `test/graph-neighborhood.test.ts` imports
  `model.ts`, which pulls it into the root type-check program (no DOM lib), so
  the runtime probes live in `useMediaQuery.ts` instead.
- render-smoke now drives the foldable geometry (933x704) directly. Collapsed
  metrics: feed pane 340px, 9 rows, first row inside the pane, document 704px so
  nothing needs to scroll. Metrics re-expanded: feed holds the 240px floor and
  the document grows to 937px, so the page scrolls to it — and scrolling to the
  middle of that document leaves the pane at exactly 240px, which is the
  end-to-end witness for the document-relative measurement. A short-desktop pass
  at 1366x640 covers the Board stats strip folding behind a working disclosure,
  with the 1366x900 converse asserting it still renders inline.
- The pre-fix numbers came from running the new probe against the base tree
  (`5afcaa4` plus `render-smoke.mjs`): feed pane **51px**, `firstRowFits: false`,
  `disclosureDisplay: none`, `scrollHeight === clientHeight` — the reported
  symptom, reproduced rather than asserted.
- Observed debt, not a disposition: the render-smoke harness intermittently fails
  with a CDP `{"code":-32000,"message":"Promise was collected"}` before any
  assertion runs — twice in roughly a dozen runs during this session, both times
  before the first assertion, both times passing on a re-run. It predates this
  change, but it matters more now, because the smoke is a required CI step and
  carries the only end-to-end proof of this fix. Nothing tracks it yet; if it
  recurs, quarantine or instrument the CDP session setup rather than re-running.
- Mutation testing during review found four assertions that passed for the wrong
  reason, including one that would have let the original bug back in: the
  `matchMedia` stub ignored its query, so re-pointing `isShortViewport` at the
  WIDTH axis kept the suite green. The unit tests now echo and assert the query,
  assert the reveal group's selectors by set equality rather than by substring,
  and cover `paneDocumentTop` and `readSafeAreaBottomPx`, which had no coverage
  at all — gutting either one had left the entire suite, `tsc` and the smoke
  green.

## 2026-08-25 — Web sidecar re-resolves its proxied upstreams

**Result**
- `docker/ui-nginx.conf` now reaches `board`, `api`, and `live` through
  per-request variables backed by the Docker embedded resolver instead of
  literal `proxy_pass` hostnames, so an upstream recreated on a new address is
  proxied to rather than 502'd against a dead one.
- The pg-compose smoke forces `api` onto a different container address and
  requires the proxy to follow it, so the regression cannot come back unseen.

**Why / context**
- nginx resolves a literal `proxy_pass` hostname exactly once, at config load,
  and pins that address for the worker's lifetime. Docker gives a recreated
  service a new address, and compose only recreates services whose own image or
  config changed — so an ordinary redeploy can move `api` or `live` while
  leaving the `web` sidecar untouched and pointing at addresses that no longer
  exist.
- The failure is close to invisible. `/` keeps serving the SPA from disk and the
  container keeps reporting healthy; only the proxied `/api/*` routes are dead,
  so nothing surfaces the break until someone opens the board. A live compose
  deployment of this stack went dark exactly that way after a routine redeploy.
  The first repair there was an operator-side restart hook, which treats the
  symptom during a deploy; this removes the cause and also covers an upstream
  that moves outside one.
- The `/api/` block needed the most care. `proxy_pass http://api:8081/api/;`
  carries a URI, so nginx replaces the matched location prefix with it — but
  that replacement is `/api/` → `/api/`, an identity mapping. Switching to a
  variable with no URI part forwards the original request URI unchanged, which
  is the same thing. Nothing under `src/` emits a `Location` header, so the
  implicit `proxy_redirect default` that a variable `proxy_pass` disables costs
  nothing here.
- `valid=10s` is deliberate: Docker's embedded DNS hands out a 600s TTL, which
  would cache the dead address straight back and undo the fix.
- One behaviour genuinely changes, and it is worth knowing about: nginx used to
  refuse to start at all when an upstream name did not resolve, so a stack
  missing `live` failed loudly at `web` startup. Deferred resolution means the
  sidecar now starts, serves the SPA, and 502s only that route. The loud failure
  moves to where it belongs — compose `depends_on` plus the deployment's own
  smoke, which already asserts `/`, `/api/live-snapshot`, and `/api/range`
  through the published web port.

**Behaviour change, measured**
- `docker run --entrypoint nginx <web:1.12.9> -t` →
  `[emerg] host not found in upstream "board"`, exit 1.
- The same test on the rebuilt image → `configuration file ... test successful`,
  exit 0.

**Evidence**
- Before: the smoke reported the forced move and then `GET /api/stats -> 502`
  for the full 60s recovery window; exit 1.
- After: same forced move, `web re-resolved api after the upstream moved`, exit
  0, with every pre-existing route assertion in the smoke still passing.
- Reproducing it needs the sentinel. Recreating `api` on its own usually gets
  the same address back from Docker's IPAM, so a naive version of this test
  passes against the broken config and proves nothing.
- `pnpm run typecheck`, `pnpm test` (612 passing), and `shellcheck` over
  `scripts/**` all clean.

**Links**
- `docker/ui-nginx.conf`, `scripts/ci/pg-compose-smoke.sh`.

**Follow-ups**
- A moved upstream still returns 502 for up to the resolver's `valid=10s`
  window before the proxy follows it. That is well inside the deploy gate's
  own wait, but a deployment that probes faster may want a short retry.
