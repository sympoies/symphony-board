# 2026-08

## 2026-08-25 — Web sidecar re-resolves its proxied upstreams

**Result**
- `docker/ui-nginx.conf` now reaches `board`, `api`, and `live` through
  per-request variables backed by the Docker embedded resolver instead of
  literal `proxy_pass` hostnames, so an upstream recreated on a new address is
  proxied to rather than 502'd against a dead one.
- The pg-compose smoke forces `api` onto a different container address and
  requires the proxy to follow it, so the regression cannot come back unseen.

**Why / context**
- nginx resolves a literal `proxy_pass` hostname exactly once, at config load,
  and pins that address for the worker's lifetime. Docker gives a recreated
  service a new address, and compose only recreates services whose own image or
  config changed — so an ordinary redeploy can move `api` or `live` while
  leaving the `web` sidecar untouched and pointing at addresses that no longer
  exist.
- The failure is close to invisible. `/` keeps serving the SPA from disk and the
  container keeps reporting healthy; only the proxied `/api/*` routes are dead,
  so nothing surfaces the break until someone opens the board. A live compose
  deployment of this stack went dark exactly that way after a routine redeploy.
  The first repair there was an operator-side restart hook, which treats the
  symptom during a deploy; this removes the cause and also covers an upstream
  that moves outside one.
- The `/api/` block needed the most care. `proxy_pass http://api:8081/api/;`
  carries a URI, so nginx replaces the matched location prefix with it — but
  that replacement is `/api/` → `/api/`, an identity mapping. Switching to a
  variable with no URI part forwards the original request URI unchanged, which
  is the same thing. Nothing under `src/` emits a `Location` header, so the
  implicit `proxy_redirect default` that a variable `proxy_pass` disables costs
  nothing here.
- `valid=10s` is deliberate: Docker's embedded DNS hands out a 600s TTL, which
  would cache the dead address straight back and undo the fix.
- One behaviour genuinely changes, and it is worth knowing about: nginx used to
  refuse to start at all when an upstream name did not resolve, so a stack
  missing `live` failed loudly at `web` startup. Deferred resolution means the
  sidecar now starts, serves the SPA, and 502s only that route. The loud failure
  moves to where it belongs — compose `depends_on` plus the deployment's own
  smoke, which already asserts `/`, `/api/live-snapshot`, and `/api/range`
  through the published web port.

**Behaviour change, measured**
- `docker run --entrypoint nginx <web:1.12.9> -t` →
  `[emerg] host not found in upstream "board"`, exit 1.
- The same test on the rebuilt image → `configuration file ... test successful`,
  exit 0.

**Evidence**
- Before: the smoke reported the forced move and then `GET /api/stats -> 502`
  for the full 60s recovery window; exit 1.
- After: same forced move, `web re-resolved api after the upstream moved`, exit
  0, with every pre-existing route assertion in the smoke still passing.
- Reproducing it needs the sentinel. Recreating `api` on its own usually gets
  the same address back from Docker's IPAM, so a naive version of this test
  passes against the broken config and proves nothing.
- `pnpm run typecheck`, `pnpm test` (612 passing), and `shellcheck` over
  `scripts/**` all clean.

**Links**
- `docker/ui-nginx.conf`, `scripts/ci/pg-compose-smoke.sh`.

**Follow-ups**
- A moved upstream still returns 502 for up to the resolver's `valid=10s`
  window before the proxy follows it. That is well inside the deploy gate's
  own wait, but a deployment that probes faster may want a short retry.
