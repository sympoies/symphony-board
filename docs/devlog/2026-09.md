# Development log - 2026-09

## 2026-09-22 - Per-file commit stats as a read-through, not a sync field

### Result

- The Commit detail pane can list the opened commit's changed files with
  per-file `+`/`-` counts and a total, laid out like `git-scope commit`
  (`[M] path   +40 -0`, then one total row).
- It is served by a new writer-owned route, `GET /api/commit-files`
  (`src/server/commit-files.ts`), and gated by a Settings toggle that is OFF by
  default (`symphony-board:commit-file-stats`).
- The pane's reading order changed with it: title, then the facts (repo,
  author, time, sha, lines, branch), then the message body, then the files. The
  facts used to sit UNDER a body that can run to dozens of lines.
- The title is now the provider link and the trailing "Open on provider" anchor
  is gone; the list row already linked its title the same way.

### Why / context

- Per-file counts cannot ride the sweep at this volume. The commit TOTALS can:
  GitHub answers 100 commits in one aliased GraphQL document, GitLab inlines
  them on the list feed. Per-file has no batch on either provider - GitHub's
  GraphQL commit exposes no file list at all (one REST call per commit) and
  GitLab serves only a raw unified diff whose counts must be read off the
  hunks. At ~700 commits/week across ~25 repos that is a different cost class.
- The harder problem was not cost but decay: an activity upsert replaces
  `details` wholesale, so a sweep that capped or skipped the enrichment would
  ERASE the breakdown an earlier sweep stored - the list would flicker in and
  out with the sweep cadence. A read-through has nothing to rot.
- Reusing the local `git-scope` CLI was considered and rejected: it needs a
  working clone (this repo is a pure API aggregator and ships as a container),
  and it has no machine-readable output. Its LAYOUT was worth copying; its
  mechanism was not. With a clone, `git show --numstat` would beat parsing it.
- The route is writer-owned for the same reason `/api/token-rate-limits` is: it
  needs config, token resolution, and outbound provider access. The configured
  project list is the allowlist, so it cannot be aimed at an arbitrary repo
  with the deployment's token, and the sha must be plain hex.

### Evidence

- `pnpm run typecheck`; `pnpm test` - 687 pass / 0 fail (670 before: 15 new
  `commit-files` cases, 1 daemon route case, 1 viewconfig case).
- `pnpm --filter @symphony-board/ui run test` and `run smoke`; UI build.
- Request contract, both providers' response shapes, the unconfigured-project
  refusal (asserts NO provider call is made), the allowlist beating a warm
  cache, single-flight dedup, and the short-lived failure cache are covered in
  `test/commit-files.test.ts`.
- Specialist review (security, api-contract, performance, testing,
  maintainability, then red-team) drove the hardening: full-length shas only
  (an abbreviation multiplied the cache keys for one commit), authorization
  ahead of the cache, negative caching with a TTL, single-flight, hunk-scoped
  diff counting, and `total_scope` so a capped list cannot mislabel its total.

### Follow-ups

- If the breakdown proves worth having offline (or for aggregate analysis such
  as per-file churn), the next step is a dedicated `commit_file_stats` table
  written only when fetched - NOT `details`, which the upsert overwrites.

## 2026-09-21 - Commit line counts, an author filter, and a reordered digest

### Result

- Commit rows and the detail pane now show `+`/`-` line counts, carried on the
  open activity `details` object as `additions` / `deletions` (contract 4.7.1,
  a clarification release — no shape changed).
- The Commits toolbar gained an author filter; `?author=` had been settable
  only from the digest rail, so it was unreachable wherever the rail collapses
  into a sheet.
- The digest rail leads with authors, then repos, commit types, branches. The
  filter surfaces (toolbar, mobile sheet) keep their repo-first order.

### Why / context

- Merge commits deliberately carry NO counts. Both providers measure a merge
  against its first parent, so any sum over a range counts the merged branch's
  work twice. They are skipped while fetching (no request spent) and dropped on
  replay, because a stored payload can hold them regardless — GitLab returns
  stats for every commit once asked, merges included.
- Absent counts mean unknown, never zero. There is no backfill: the counts are
  not in raw payloads written before this, and `normalize` is pure, so a
  replay cannot invent them. Older commits gain them only if a later full
  sweep re-reads them.
- The author options keep bot accounts even though the rail ranking drops
  them. A ranking answers "who are the top people"; a filter answers "show me
  only these rows", and hiding a bot there would leave visible rows with no way
  to select them.

### Evidence

- Provider costs measured against the live APIs before implementing. GitHub's
  REST commit feeds carry no `stats` at all (single-commit only); aliasing 100
  `object(oid:)` lookups into one GraphQL document returned all 100 for
  `rateLimit.cost = 1`. GitLab's list feed inlines `stats` with
  `with_stats=true` for zero extra requests, while its compare feed never does,
  so only compare-derived shas cost a single-commit GET (bounded at 200 per
  project per sweep).

  commits, all with counts (`+55 -15`, `+241 -26`, `+202 -9`), sweep complete.
- 662 repository tests, 455 UI tests, UI build, and render smoke all passed;

## 2026-09-14 - Releasing stopped depending on a terminal staying alive

### Result
- `publish-image.yml` accepts `workflow_dispatch` with a `tag` and a `push`
  input that defaults to false, so a change to the workflow can be exercised
  against an existing tag without publishing anything.
- A `release-complete` job verifies the three desktop assets reached the
  Release. With the existing GHCR manifest verification, a green run now means
  the release carries every artifact.
- `release.sh --execute` returns once the Release exists and no longer waits
  for that run. `--wait` opts back into the old blocking behaviour; `--resume`
  still waits, because waiting is what it is for.

### Why / context
- The wait was the fragile half of a release. It blocks for the tens of minutes
  the emulated arm64 build takes, and it was killed repeatedly — leaving
  releases published but unverified, which is what `--resume` had to be written
  to recover. Moving the completeness check into CI removes the thing that kept
  breaking rather than making it more robust.
- The workflow had no trigger but `release: published`, so every edit to it
  shipped unverified. One of those edits — an arm64 build that died under QEMU —
  cost v1.22.0 its container images, and nothing could have caught it before the
  release. A manual run is how that file becomes testable.
- A manual run must change nothing that outlives it, and the release event is
  empty on one. Three workflow-level values (`RELEASE_TAG`, `PUBLISH`,
  `MOVE_LATEST`) resolve that once instead of letting each step guess;
  `MOVE_LATEST` exists because a bare `!github.event.release.prerelease` reads
  as true on a manual run and would move `latest`.
- `release-complete` cannot express its condition with `env.PUBLISH`: GitHub
  does not expose the `env` context in a job-level `if`, so it would evaluate
  empty and silently skip the job that decides completeness. The difference
  between a working guard and a dead one is four spaces of indentation, so a
  test asserts no job-level condition reads `env`.
- `--dry-run` previews `--execute`, so it inherits the same default. Announcing
  a wait that will not happen is worse than silence: it is the line an operator
  reads before deciding whether to sit and watch.
- `--execute` still discovers the run, it just does not watch it. "Did a run
  start at all?" is the one failure CI cannot report -- Actions disabled, the
  workflow broken on `main`, a concurrency group holding it -- because there is
  no red run to notice when there is no run. Exiting 0 on that would be a
  reassuring lie, so discovery and the watch are now separate functions.
- `tag` is free text and every job checks that ref out, so a manual run could
  have named a BRANCH: push `v9.9.9` with a matching `package.json`, pass the
  version gate (which compares the tag's shape to the checked-out tree, both
  attacker-controlled), and have that branch's `Dockerfile` and packaging
  scripts built and published as a release, with `packages: write` and
  `contents: write`. Tag protection does not apply to a newly pushed branch.
  The jobs now check out `refs/tags/<tag>`, which a branch cannot satisfy, and
  the version gate refuses a ref origin does not carry as a tag.
- The concurrency group keyed on `github.ref`, which differs between a release
  run and a manual run for the same tag, so a publishing manual run could race
  the real release run -- both pushing the same GHCR tags, both clobbering the
  same assets. It now keys on the tag.

### Evidence
- `pnpm run typecheck` and `pnpm test` (650 tests) clean; `shellcheck
  scripts/release.sh` clean.
- New `test/release-script.test.ts` cases pin the execute default, the `--wait`
  opt-in, the dry-run preview, and the failure when no run appears; each was
  observed red first. The execute fixture gets a real commit and a local origin
  via `insteadOf`, which keeps the repo slug while answering `ls-remote`
  locally.
- The fixture's first CI run was red where local was green: it makes a real
  commit, and a runner has no git identity to borrow. Rather than only adding
  one, `cleanGitEnv` now reads no user or system git config at all, so a
  fixture that silently depends on the host fails on the developer machine too.
- New `test/release-dispatch-workflow.test.ts` cases pin the manual-run safety
  properties and the `RELEASE_TAG` plumbing. Ten mutations were run against the
  finished guards and all ten were caught: inverting `release-complete`'s
  condition, deleting its non-zero exit, weakening `grep -Fxq` to `grep -Fq`,
  reverting the version gate to the trigger ref, dropping a checkout's
  `refs/tags` qualifier, removing the tag-existence gate, dropping an image
  tag's semver value, reverting the concurrency group, writing a job condition
  as a folded scalar (which the line-based guards would otherwise never read),
  and removing execute's run discovery.

### Links
- sympoies/symphony-board#639 — the interrupted publish wait. `--resume`
  patched the recovery path; this removes the wait that needed recovering.

### Follow-ups
- None. The manual trigger was exercised from the branch before merge --
  `gh workflow run publish-image.yml --ref ci/publish-dispatch -f tag=v1.23.0
  -f push=false` -- and went green end to end while pushing nothing. Dispatching
  did not require the change to be on the default branch first, so the workflow
  is testable before it ships, which was the whole point.
- The one path this cannot exercise before merge is `release: published` through
  the new `env` block, which only a real release runs.

## 2026-09-14 - The board image stopped installing its deps under QEMU

### Result
- `docker/Dockerfile` resolves dependencies in a `$BUILDPLATFORM` stage and
  copies `node_modules` into the target-arch runtime, so no Node or pnpm process
  runs under emulation during a cross-arch build.
- A test pins that for both images, and pins the detector itself.

### Why / context
- v1.22.0's `publish-image` failed twice in a row at the same step:
  `qemu: uncaught target signal 4 (Illegal instruction)` inside
  `corepack enable && corepack prepare pnpm && pnpm install`, building
  linux/arm64 on an amd64 runner. Two identical consecutive failures is not a
  flake, and it was initially called one because v1.17.0's single failure had
  cleared on a re-run.
- It is not this repository's code. The same arm64 build, same Dockerfile, same
  base image, succeeds under a local QEMU of a different version. What changed is
  the runner's emulator, which is not something to fix by pinning a version and
  hoping.
- Nothing about the dependency tree needs the target architecture. Both
  production dependencies are pure JavaScript — postgres.js ships no native
  binding and has no build step, and the contract package is JS plus JSON — so
  `node_modules` is architecture-independent. Running pnpm under emulation to
  produce it bought nothing and was the only thing that could fail.
- `ui.Dockerfile` already used `FROM --platform=$BUILDPLATFORM node:24-alpine AS
  build`. The pattern was the house style; the board image was simply the one
  that had not adopted it, which is exactly why it was the one that died while
  the web image built fine.

### Evidence
- Reproduced the whole pipeline locally before changing anything: the arm64
  build of the UNCHANGED Dockerfile succeeds here, which is what established the
  emulator rather than the file as the variable.
- After the change, both architectures build, and both pass the two checks CI
  runs against the board image: the contract validator against the sample
  contract, and the postgres runtime import. The arm64 image reports
  `arm64 linux`, `node v24.21.0 arm64`, resolves postgres.js through the copied
  pnpm symlink tree, and still has npm stripped from the runtime layer.
- The guard goes red against the previous Dockerfile and green against this one.
- Its own detector is tested. The first cut matched the tool names anywhere in a
  line and flagged `rm -rf .../npm`, `chmod pnpm-lock.yaml` and
  `chown node:node` as emulated installs — three false positives with nothing to
  distinguish them from a real one. It now reads command heads, and a case pins
  both directions.
- Type-check clean; 643 backend tests.

### Follow-ups
- `publish-image.yml` runs only on `release: published`, so a change to it cannot
  be exercised without cutting a release. That is why this was fixed in the
  Dockerfile, which is testable locally, rather than by restructuring the
  workflow onto native arm64 runners — which is the better long-term shape now
  that free arm64 runners exist for public repositories, and is unverifiable
  until the workflow gains a manual trigger.
- v1.22.0 remains published with macOS and APK assets but no container images.
  Its tag predates this fix, so re-running its workflow would rebuild the old
  Dockerfile; the images arrive with the next release.

## 2026-09-14 - render-smoke stopped waiting a minute into every run

### Result
- Each `waitHtml` / `waitValue` / `waitForCapabilitiesRequests` call now gets its
  own budget instead of sharing one wall-clock deadline computed at startup, with
  a run-wide backstop so a pathological hang still ends.
- A wait that gives up says so. The summary carries a `no waits timed out (N)`
  check and prints the first ten, because the old silence is what made this
  expensive.

### Why / context
- `DEADLINE_MS` was 60s and `deadline` was computed once. The suite has long
  since grown past five minutes, so from about the one-minute mark every wait
  returned on its first check. The later half of the run was not waiting for
  anything; it passed only when the machine happened to be fast enough for the
  fixed `sleep()`s already between steps.
- The failure is silent and it is misattributed by construction. A wait that
  stops waiting does not report a timeout — the probe downstream reads an
  unrendered page and reports `found: false`, which reads as a layout defect on
  whatever page it names. On a loaded machine this produced ~77 interleaved
  failures across pages the change under test had never touched, and a
  `graph:top=0` that read 327 on a clean build. Time went into the pages named
  in those failures before the harness was suspected.
- It only bites under load, which is why CI never showed it: a fast unloaded
  runner renders inside the existing sleeps, so the missing wait costs nothing
  there. That asymmetry is worth naming — the suite was least trustworthy exactly
  where it was being used interactively.
- The per-wait budget is 15s: long enough to absorb a loaded box, short enough
  that a genuinely broken page still fails promptly. The run-wide cap is 15
  minutes and is a backstop, not a budget; a healthy run never approaches it.
- `envPort` was NOT reused for these durations even though it was the obvious
  helper to hand. It rejects anything above 65535, so a run budget expressed in
  milliseconds would have failed with an "invalid port" error the first time
  anyone overrode it.

### Evidence
- Written against the unchanged script first: the budget helper did not exist, so
  the new test file could not import it.
- The structural assertions are the ones that matter here, because the unit
  arithmetic is trivial: each wait helper must derive its own deadline rather
  than close over the shared one, and the timeout detail must print in the board
  summary. Both catch a regression the arithmetic cannot see.
- The second of those was written because the first revision of this change put
  the detail print in the standalone-setup branch by accident. A failing run
  reported `no waits timed out (68)` and then not one of the 68 — the same shape
  of defect as the bug being fixed, a diagnostic that reads as present while
  doing nothing.
- Type-check clean; 437 UI tests (432 before, plus five).

### Links
- [`packages/ui/scripts/smoke-wait.mjs`](../../packages/ui/scripts/smoke-wait.mjs)
- [`packages/ui/test/smoke-wait.test.ts`](../../packages/ui/test/smoke-wait.test.ts)

### Follow-ups
- With waits restored, this machine reports 68 timeouts on a full run, mostly in

## 2026-09-14 - An interrupted release can be resumed

### Result
- `scripts/release.sh --resume` re-attaches to an already-created GitHub Release,
  waits for its `publish-image` run, and then runs the same verification an
  interrupted `--execute` never reached. It mutates nothing.
- `--execute`'s "release already exists" refusal now names that recovery command
  instead of leaving the operator to reconstruct it.
- The three v1.15.0 / v1.17.0 / v1.18.0 release runs recorded as "OOM-killed"
  were killed for memory, but not the way that phrasing implies, and not for
  anything the script itself did. See the correction below.

### Why / context
- `--execute` creates the Release and then blocks for tens of minutes on
  `gh run watch`, because `publish-image` builds `linux/arm64` under emulation.
  If that wait dies for any reason, the Release is published but unverified, and
  the script had no state for it: `--execute` refuses to run again (the Release
  exists) and `--verify-only` reads GHCR immediately, so it fails outright while
  the workflow is still in flight. Both halves of that trap had to be closed, so
  resume is a mode rather than a flag on an existing one.
- Resume resolves the commit from the Release's `targetCommitish`, not from
  local `HEAD`. The checkout has usually moved on by the time anyone resumes,
  and `publish-image` runs are matched by head SHA — resuming against `HEAD`
  would wait out the discovery timeout for a run that cannot exist.
- Resume takes both the released commit and the prerelease flag from the Release
  itself. Review caught the second one: prerelease was still read from the
  `--prerelease` flag, so resuming a prerelease would have verified the `latest`
  tag belonging to some earlier non-prerelease and reported the release complete
  having asserted nothing about it. Resume exists because the original
  invocation's flags are gone, so any value it reconstructs from operator memory
  is the same defect in a different place.
- Resume is exempt from the cut-time gates (per-app version drift, version match
  against `package.json`, clean tree, `main` alignment) for the same reason
  `--verify-only` is: it inspects an already-published release and creates
  nothing. Applying the version gate would make a release cut from an older
  commit unresumable, which is precisely the case resume exists for.
- The kill mechanism is the session harness's memory-pressure killer, not the
  kernel's OOM killer, and the distinction is what makes the follow-up obvious.
  The kernel recorded six `oom-kill` events this boot, all on 2026-09-12, all
  against a ~40GB Node process, and none on the release days. The release runs
  ended instead with the harness's bare `[killed]` marker — not a process exit
  status, and not the `137` a kernel OOM produces. The same harness later killed
  a `pr merge` on this machine with the explicit reason "stopped because the
  system is running low on memory", producing that identical marker, and the
  merge succeeded immediately when re-run in the foreground.
- So the script is not being killed for its own footprint; it is collateral for
  whole-machine pressure, which is the only reading that explains a
  twenty-second-old idle `gh run list` poller dying. Making the script leaner
  would change nothing. Any sufficiently long foreground wait will keep being
  collateral on a loaded box, which is why `--resume` is a recovery rather than
  a cure, and why moving the wait into CI is the recorded follow-up.
- An earlier version of this entry claimed the runs "were never an OOM". That
  over-corrected a wrong diagnosis into a different wrong one, and is fixed here
  rather than quietly dropped. The releases themselves were always fine; what
  was missing was a way to finish them.

### Evidence
- Four tests written first against the unchanged script, all failing: resume
  rejected as `unknown argument: --resume` (three tests) and the `--execute`
  refusal carrying no recovery hint. All four pass after the change.
- Review then mutation-tested those four and proved three gaps they could not
  see: dropping the exit status from the publish wait left every test green
  while resume reported `complete` over a FAILED workflow; the empty-commit
  guard could be deleted undetected; and the run matcher could accept any run
  regardless of head SHA, because the stub returned one SHA for both the release
  and the run. The suite is now 14 cases, with a decoy run that has to be
  rejected and a short discovery timeout so a matcher regression fails in
  seconds instead of hanging the suite for two minutes.
- The stubbed-`gh` fixture covers the parts a live run cannot: a release that
  does not exist, and a released commit that differs from the checkout's `HEAD`.
- Exercised live against the real v1.18.0 release, which had been left unverified
  by exactly this failure. Resume resolved `b880dfc0`, found run `34775915656`,
  saw it already complete, and verified four GHCR manifests
  (`linux/amd64 linux/arm64`) plus three desktop assets.
- Type-check clean; 639 backend tests pass (630 before, plus the nine new).

### Links
- [`scripts/release.sh`](../../scripts/release.sh)
- [`RELEASING.md`](../../RELEASING.md) — "Resuming An Interrupted Release"
- [`test/release-script.test.ts`](../../test/release-script.test.ts)

### Follow-ups
- The underlying fragility is unchanged: a release still depends on one
  long-lived foreground wait. Resume makes the recovery one command instead of a
  manual reconstruction, but it does not make the wait survivable. Moving the
  wait into CI would.

## 2026-09-13 - Primary pages fill the shell on wide displays (v1.14.0)

### Result
- Live, Items, Graph and Reviews now track the full-bleed app shell instead of
  stopping at a `1580px` page cap, so no display wider than ~1620 CSS px strands
  a dead right gutter any more.
- `render-smoke` gained a wide-viewport probe that measures every primary page
  against the shell's content box at the four displays this board is actually
  driven on.
- Shipped as v1.14.0, with the macOS thin client updated on the Apple Silicon
  workstation and the signed universal APK delivered to the foldable.

### Why / context
- The shell has always been full-bleed (`.app-wide` sets `max-width: none`), but
  each page carried its own cap with no auto margin. The header and tab strip
  therefore reached the window edge while the content stopped short and stayed
  left-aligned — the mismatch was the visible symptom, not the width itself.
- Width is now governed further in, where it stays proportional: the
  master-detail splits balance by ratio through `--master-detail-columns`, and
  prose keeps its own reading measure (100ch on Live, 92ch on Items). Moving the
  limit from the page to the text is what makes full-bleed safe.
- Reviews needed BOTH of its caps removed. Its facet chrome and its
  master-detail content are siblings rather than nested, so capping either alone
  left the two halves of one column misaligned.
- `.commits-page` deliberately keeps its `1180px` cap: a single-column list has
  no second pane to absorb width, so a measure limit is the right design there
  rather than a leftover. The Activity grid is unchanged for the same reason.
- The assessment behind the scope decision found the SMALL end of the device
  range already covered — the dual-axis layout tiers, the `paper` e-ink theme and
  the Android thin client already handle the foldable inner screen (~933x704),
  the e-ink tablet (936x702) and the phone (~384x832). Only the wide end was
  unfinished, so only that was taken.

### Evidence
- The probe was written first and failed on the unchanged stylesheet, with
  shortfalls of 108px at 1728x1010, 300px at 1920x1080, 940px at 2560x1440 and
  2220px at 3840x2160. After the fix it reports `covered 16/16, short []`.
- Type-check clean, 630 backend tests, 398 UI tests (including
  `layout-tier.test.ts`, which pins the stylesheet to the tier constants), UI
  build clean, render smoke PASS. CI 12/12 on both PRs.
- One CI red on the first run was `test/live-telegram.test.ts` — a timing-
  sensitive Telegram-bridge assertion unrelated to this diff; it passed 5/5
  locally and green on re-run.
- Release assets verified: both GHCR images for `1.14.0` and `latest` across
  amd64/arm64, the two macOS arm64 bundles, and the signed universal APK.
  Downloaded artifact digests matched the published ones before install.
