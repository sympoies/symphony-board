## 2026-09-14 — The branch picker joins the repo filter

**Result**
- The Commits toolbar keeps its two filters together on the left instead of
  pushing the branch picker to the far right edge.

**Why / context**
- They are one filter group. Under `justify-content: space-between` they sat at
  the two ends of a full-width toolbar, so picking a repo and then a branch meant
  crossing the page — on a 3008px display, most of it.
- The repo filter keeps its exact width: its flex-basis is set to the max it was
  already growing to, so dropping the grow moves the branch picker without
  resizing anything else.
- The narrow tier already stacks this toolbar into a column and is untouched.

**Evidence**

  space after it, `stacked: false` and `topDelta: 1px`. It was spread to the
  edges before.
- The smoke now asserts the two sit adjacent. The existing check only asserted
  the repo comes first in DOM order, which held either way and would not have
  noticed this.
- Type-check clean; 441 UI tests.

  twelve render-smoke assertions on `.live-rank-*` keep working; only the axis
  and gridlines drop, because a shared vertical axis means nothing once the bars
  run horizontally.

**Evidence**

- Labels at 3008: `android-thin-client-sh` renders at 208px complete, against

## 2026-09-14 — A ceiling inside a track that no longer had one

**Result**
- The Activity overview panel fills its column. It kept `inline-size: min(100%,
  680px)` after v1.19.0 removed the column's own ceiling, so at 3008px the track
  was 1030px and the panel was 680 — a 363px hole between the overview and the
  rail.
- Commits gives the list the lead on a very wide display: 1600px list against a
  700px sidebar rail, stacked rather than two-up, with the remainder shared as
  symmetric margin. It was a 1180px list beside a 1776px rail that was a third
  its height.
- `.live-feed` joined the shared auto-hiding scrollbar set it had been missing
  from, so the Live feed's gutter matches every other scroller.

**Why / context**
- The overview is the same defect as the page caps, two levels in. Removing a
  ceiling from a track does nothing if the pane inside keeps its own; the dead
  space just moves. Worth stating as a rule because it has now happened at three
  levels: page, column, pane.
- The calendar inside that panel is a fixed 9px-cell grid with a natural width
  of about 640px and simply sits left. That is content sizing and is fine — the
  stat rows, the trend chart and the top-repo bars are what use the extra width.
- The Commits ratio was backwards at 4K: the supporting rail was wider than the
  primary list. The 1180px reading cap protects a commit row from becoming a
  thin ribbon, which is not a reason to hand the surplus to the rail. Dropping
  the rail out of the two-up tier matters as much as the widths — split into a
  700px sidebar it would have given ~344px panes, narrower than its six-bar
  charts read at, and short enough to strand height beside a 1252px list.
- The centring at this tier is deliberate and is NOT a return of #631. That was
  a split sitting visibly inset from full-bleed chrome at ordinary widths; this
  engages only where the page has more room than it needs, and 328px of
  symmetric margin reads as intent rather than misalignment.
- `.live-feed` was the only inner scroller outside the shared `:where(...)` set,
  so it got the platform default bar — full width, always painted — sitting
  between the feed cards and the detail pane where it read as extra gap against
  the flat 12px of the metric cards above. The reported symptom was the gap; the
  cause was a missing selector.

**Evidence**
- Measured before and after at the viewport actually in use (3008x1692, the
  scaled mode this 4K panel runs at), not at 3840x2160:

  | | before | after |
  | --- | --- | --- |
  | Activity column gaps | `[12, 363]` | `[12, 12]` |
  | Activity overview panel | 680px in a 1030px track | 1030px |
  | Commits list / rail | 1180 / 1776, rail 494 tall | 1600 / 700, rail 783 tall |
  | Commits gutters | 0 / 0 | 328 / 328 |

  At 1900px both pages are unchanged: `[12, 12]` and `[12]`, gutters 0.
- The render-smoke probe gained the measurement that would have caught this: the
  widest gap BETWEEN adjacent columns, at 1212, 1280 and 3008. The existing
  check measured only the rightmost edge, so a hole between two columns reported
  zero — which is exactly why 363px shipped.
- Reverting `inline-size: 100%` to the ceiling turns the new assertion red;
  restoring it turns it green.
- Type-check clean; 437 UI tests; 639 backend tests.

**Follow-ups**
- The Commits rail is 783px against a 1252px list at 4K, so roughly 470px under
  it is still empty. Five panes only need so much height; closing that means
  more panes or a different rail, not a width change.

## 2026-09-14 — render-smoke stopped waiting a minute into every run

**Result**
- Each `waitHtml` / `waitValue` / `waitForCapabilitiesRequests` call now gets its
  own budget instead of sharing one wall-clock deadline computed at startup, with
  a run-wide backstop so a pathological hang still ends.
- A wait that gives up says so. The summary carries a `no waits timed out (N)`
  check and prints the first ten, because the old silence is what made this
  expensive.

**Why / context**
- `DEADLINE_MS` was 60s and `deadline` was computed once. The suite has long
  since grown past five minutes, so from about the one-minute mark every wait
  returned on its first check. The later half of the run was not waiting for
  anything; it passed only when the machine happened to be fast enough for the
  fixed `sleep()`s already between steps.
- The failure is silent and it is misattributed by construction. A wait that
  stops waiting does not report a timeout — the probe downstream reads an
  unrendered page and reports `found: false`, which reads as a layout defect on
  whatever page it names. On a loaded machine this produced ~77 interleaved
  failures across pages the change under test had never touched, and a
  `graph:top=0` that read 327 on a clean build. Time went into the pages named
  in those failures before the harness was suspected.
- It only bites under load, which is why CI never showed it: a fast unloaded
  runner renders inside the existing sleeps, so the missing wait costs nothing
  there. That asymmetry is worth naming — the suite was least trustworthy exactly
  where it was being used interactively.
- The per-wait budget is 15s: long enough to absorb a loaded box, short enough
  that a genuinely broken page still fails promptly. The run-wide cap is 15
  minutes and is a backstop, not a budget; a healthy run never approaches it.
- `envPort` was NOT reused for these durations even though it was the obvious
  helper to hand. It rejects anything above 65535, so a run budget expressed in
  milliseconds would have failed with an "invalid port" error the first time
  anyone overrode it.

**Evidence**
- Written against the unchanged script first: the budget helper did not exist, so
  the new test file could not import it.
- The structural assertions are the ones that matter here, because the unit
  arithmetic is trivial: each wait helper must derive its own deadline rather
  than close over the shared one, and the timeout detail must print in the board
  summary. Both catch a regression the arithmetic cannot see.
- The second of those was written because the first revision of this change put
  the detail print in the standalone-setup branch by accident. A failing run
  reported `no waits timed out (68)` and then not one of the 68 — the same shape
  of defect as the bug being fixed, a diagnostic that reads as present while
  doing nothing.
- Type-check clean; 437 UI tests (432 before, plus five).

**Links**
- [`packages/ui/scripts/smoke-wait.mjs`](../../packages/ui/scripts/smoke-wait.mjs)
- [`packages/ui/test/smoke-wait.test.ts`](../../packages/ui/test/smoke-wait.test.ts)

**Follow-ups**
- With waits restored, this machine reports 68 timeouts on a full run, mostly in
  the `#/debug` fill tabs and the portrait sweep. That is now visible rather than
  silently passing junk downstream, but it is not explained, and it is not the
  same question as this change. CI is green, so it is local to this host.
- `render-smoke` still binds a fixed port with no cleanup on abort, so an
  orphaned server can serve a stale `dist/` to a later run.

## 2026-09-14 — Wide layout stopped stacking like a phone on the foldable

**Result**
- The Android wide-layout setting pins the WebView viewport to exactly 1280 CSS
  px. Both two-pane pages stacked above that width, so a foldable with the
  setting on got desktop chrome with phone stacking: the Commits rail sat under
  a full-width list, and the Activity feed sat in a 720px column with 441px of
  measured dead gutter beside it.
- Both now share one floor, `SPLIT_RAIL_MIN_WIDTH_PX`, sized from the tracks
  rather than picked round, and `layout-tier.test.ts` compares it against
  `WIDE_VIEWPORT_WIDTH`.
- The Activity overview column takes the leftover instead of capping at 680px,
  which also closes a dead gutter that ran from ~1412px to the 1700px rail tier
  on ordinary laptops.
- The Live metric strip can be collapsed at every size, not only on a viewport
  the compact tier already claims.

**Why / context**
- The two stack breakpoints (1450px for Activity, 1500px for Commits) predate
  the wide-layout setting and were never compared with it. Nothing in the build
  read both numbers, so the pair could not drift *detectably* — the regression
  test that now compares them is the real fix; moving the numbers is the easy
  half.
- The floor is a VIEWPORT width while the track sizes are content-box widths, so
  the page padding is not in it. At exactly 1212px the feed sits at 590px rather
  than its preferred 640px, which `minmax(0, …)` allows deliberately: nothing is
  stranded and nothing overflows. It reaches 640px by 1280px, which is the width
  that actually had to work.
- The Live strip's disclosure was revealed only by the compact tier, on the
  principle that a roomy viewport shows the real control inline instead. That
  principle does not hold for this one: the disclosure IS the only control for
  the strip, so hiding it means ~300px cannot be dismissed at all. A foldable in
  landscape with wide layout on lands at 1280x891 — too wide for the narrow
  tier, too tall for the short one — and kept a feed sliver. The strip's DEFAULT
  state still follows the short tier; only the ability to override it is now
  universal.
- The Commits probe asserted the rail *stacks* at 1280px, which is precisely the
  reported defect written down as an expectation. It was correct when 1280 sat
  below the old 1500px breakpoint, and it moved to 1024px rather than being
  loosened.

**Evidence**
- Three tests written first and failing on the unchanged stylesheet; the first
  failed to import a constant that did not exist yet.
- The render-smoke probe now measures the stranded width, which is what the
  screenshots showed and what no existing probe could see. Across the floor:
  1211px gives one 720px column with `deadRight: 441`; 1212px gives
  `590px 560px` with `deadRight: 0`; 1280px gives `640px 578px` with
  `deadRight: 0`. Commits at 1280px: list 918, rail 300, `deadRight: 0`.
- Review then mutation-tested the three, and two were weaker than they read.
  The Live test matched the collapse rule against the whole stylesheet, so
  leaving the reveal at top level while the collapse stayed tier-gated passed
  everything with the button visibly inert at 1280x891; it now asserts the rule
  is in no tier. And `deadRight` was measured against the layout's own box, which
  a cap on any ancestor shrinks too — adding `.activity-page { max-width: 1100px }`
  stranded 130px and still reported 0. It measures against the shell content box
  now, and rejects a negative value so a right overflow cannot read as a fit.
  Both mutations go red after the change.
- A `graph:top=0` smoke failure during this work was checked against a clean
  build before being acted on, and was a flake — it reads 327 on both. Later
  runs on this machine produced ~77 interleaved `found:false` failures across
  unrelated pages with swap fully exhausted; the render smoke that gates this
  change is the CI one, on a clean machine.
- Type-check clean, 432 UI tests, 630 backend tests, render-smoke PASS.

- [`packages/ui/test/layout-tier.test.ts`](../../packages/ui/test/layout-tier.test.ts)

## 2026-09-14 — An interrupted release can be resumed

**Result**
- `scripts/release.sh --resume` re-attaches to an already-created GitHub Release,
  waits for its `publish-image` run, and then runs the same verification an
  interrupted `--execute` never reached. It mutates nothing.
- `--execute`'s "release already exists" refusal now names that recovery command
  instead of leaving the operator to reconstruct it.
- The three v1.15.0 / v1.17.0 / v1.18.0 release runs recorded as "OOM-killed"
  were killed for memory, but not the way that phrasing implies, and not for
  anything the script itself did. See the correction below.

**Why / context**
- `--execute` creates the Release and then blocks for tens of minutes on
  `gh run watch`, because `publish-image` builds `linux/arm64` under emulation.
  If that wait dies for any reason, the Release is published but unverified, and
  the script had no state for it: `--execute` refuses to run again (the Release
  exists) and `--verify-only` reads GHCR immediately, so it fails outright while
  the workflow is still in flight. Both halves of that trap had to be closed, so
  resume is a mode rather than a flag on an existing one.
- Resume resolves the commit from the Release's `targetCommitish`, not from
  local `HEAD`. The checkout has usually moved on by the time anyone resumes,
  and `publish-image` runs are matched by head SHA — resuming against `HEAD`
  would wait out the discovery timeout for a run that cannot exist.
- Resume takes both the released commit and the prerelease flag from the Release
  itself. Review caught the second one: prerelease was still read from the
  `--prerelease` flag, so resuming a prerelease would have verified the `latest`
  tag belonging to some earlier non-prerelease and reported the release complete
  having asserted nothing about it. Resume exists because the original
  invocation's flags are gone, so any value it reconstructs from operator memory
  is the same defect in a different place.
- Resume is exempt from the cut-time gates (per-app version drift, version match
  against `package.json`, clean tree, `main` alignment) for the same reason
  `--verify-only` is: it inspects an already-published release and creates
  nothing. Applying the version gate would make a release cut from an older
  commit unresumable, which is precisely the case resume exists for.
- The kill mechanism is the session harness's memory-pressure killer, not the
  kernel's OOM killer, and the distinction is what makes the follow-up obvious.
  The kernel recorded six `oom-kill` events this boot, all on 2026-09-12, all
  against a ~40GB Node process, and none on the release days. The release runs
  ended instead with the harness's bare `[killed]` marker — not a process exit
  status, and not the `137` a kernel OOM produces. The same harness later killed
  a `pr merge` on this machine with the explicit reason "stopped because the
  system is running low on memory", producing that identical marker, and the
  merge succeeded immediately when re-run in the foreground.
- So the script is not being killed for its own footprint; it is collateral for
  whole-machine pressure, which is the only reading that explains a
  twenty-second-old idle `gh run list` poller dying. Making the script leaner
  would change nothing. Any sufficiently long foreground wait will keep being
  collateral on a loaded box, which is why `--resume` is a recovery rather than
  a cure, and why moving the wait into CI is the recorded follow-up.
- An earlier version of this entry claimed the runs "were never an OOM". That
  over-corrected a wrong diagnosis into a different wrong one, and is fixed here
  rather than quietly dropped. The releases themselves were always fine; what
  was missing was a way to finish them.

**Evidence**
- Four tests written first against the unchanged script, all failing: resume
  rejected as `unknown argument: --resume` (three tests) and the `--execute`
  refusal carrying no recovery hint. All four pass after the change.
- Review then mutation-tested those four and proved three gaps they could not
  see: dropping the exit status from the publish wait left every test green
  while resume reported `complete` over a FAILED workflow; the empty-commit
  guard could be deleted undetected; and the run matcher could accept any run
  regardless of head SHA, because the stub returned one SHA for both the release
  and the run. The suite is now 14 cases, with a decoy run that has to be
  rejected and a short discovery timeout so a matcher regression fails in
  seconds instead of hanging the suite for two minutes.
- The stubbed-`gh` fixture covers the parts a live run cannot: a release that
  does not exist, and a released commit that differs from the checkout's `HEAD`.
- Exercised live against the real v1.18.0 release, which had been left unverified
  by exactly this failure. Resume resolved `b880dfc0`, found run `34775915656`,
  saw it already complete, and verified four GHCR manifests
  (`linux/amd64 linux/arm64`) plus three desktop assets.
- Type-check clean; 639 backend tests pass (630 before, plus the nine new).

**Links**
- [`scripts/release.sh`](../../scripts/release.sh)
- [`RELEASING.md`](../../RELEASING.md) — "Resuming An Interrupted Release"
- [`test/release-script.test.ts`](../../test/release-script.test.ts)

**Follow-ups**
- The underlying fragility is unchanged: a release still depends on one
  long-lived foreground wait. Resume makes the recovery one command instead of a
  manual reconstruction, but it does not make the wait survivable. Moving the
  wait into CI would.

## 2026-09-13 — Primary pages fill the shell on wide displays (v1.14.0)

**Result**
- Live, Items, Graph and Reviews now track the full-bleed app shell instead of
  stopping at a `1580px` page cap, so no display wider than ~1620 CSS px strands
  a dead right gutter any more.
- `render-smoke` gained a wide-viewport probe that measures every primary page
  against the shell's content box at the four displays this board is actually
  driven on.
- Shipped as v1.14.0, with the macOS thin client updated on the Apple Silicon
  workstation and the signed universal APK delivered to the foldable.

**Why / context**
- The shell has always been full-bleed (`.app-wide` sets `max-width: none`), but
  each page carried its own cap with no auto margin. The header and tab strip
  therefore reached the window edge while the content stopped short and stayed
  left-aligned — the mismatch was the visible symptom, not the width itself.
- Width is now governed further in, where it stays proportional: the
  master-detail splits balance by ratio through `--master-detail-columns`, and
  prose keeps its own reading measure (100ch on Live, 92ch on Items). Moving the
  limit from the page to the text is what makes full-bleed safe.
- Reviews needed BOTH of its caps removed. Its facet chrome and its
  master-detail content are siblings rather than nested, so capping either alone
  left the two halves of one column misaligned.
- `.commits-page` deliberately keeps its `1180px` cap: a single-column list has
  no second pane to absorb width, so a measure limit is the right design there
  rather than a leftover. The Activity grid is unchanged for the same reason.
- The assessment behind the scope decision found the SMALL end of the device
  range already covered — the dual-axis layout tiers, the `paper` e-ink theme and
  the Android thin client already handle the foldable inner screen (~933x704),
  the e-ink tablet (936x702) and the phone (~384x832). Only the wide end was
  unfinished, so only that was taken.

**Evidence**
- The probe was written first and failed on the unchanged stylesheet, with
  shortfalls of 108px at 1728x1010, 300px at 1920x1080, 940px at 2560x1440 and
  2220px at 3840x2160. After the fix it reports `covered 16/16, short []`.
- Type-check clean, 630 backend tests, 398 UI tests (including
  `layout-tier.test.ts`, which pins the stylesheet to the tier constants), UI
  build clean, render smoke PASS. CI 12/12 on both PRs.
- One CI red on the first run was `test/live-telegram.test.ts` — a timing-
  sensitive Telegram-bridge assertion unrelated to this diff; it passed 5/5
  locally and green on re-run.
- Release assets verified: both GHCR images for `1.14.0` and `latest` across
  amd64/arm64, the two macOS arm64 bundles, and the signed universal APK.
  Downloaded artifact digests matched the published ones before install.

**Links**
- Assessment and scope decision: <https://github.com/sympoies/symphony-board/issues/623>
- Wide-display fill: <https://github.com/sympoies/symphony-board/pull/624>
- Version bump: <https://github.com/sympoies/symphony-board/pull/625>
- Release: <https://github.com/sympoies/symphony-board/releases/tag/v1.14.0>

**Follow-ups**
- Options B (ultrawide layout above ~2200px, where widening two panes only
  converts gutter into slack) and C (4K legibility — ~165 hard-coded
  `font-size: NNpx` against 8 `rem`, best solved with one `--ui-scale` token plus
  a density control rather than 165 edits) are recorded in issue #623 and were
  deliberately not taken.
- `render-smoke` computes a single `deadline` at startup that every `waitHtml` /
  `waitValue` closes over, but the suite now runs ~91s against that 60s budget,
  so late waits return immediately instead of blocking. Pre-existing and
  unrelated to this change; worth its own fix in the harness.

## 2026-09-10 — Separate maintenance principles from detailed procedures

  boundaries, routine workflow, and canonical documentation routing.
